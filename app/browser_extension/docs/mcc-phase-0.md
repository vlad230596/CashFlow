# Этап 0: база знаний MCC и банковских правил

## Цель

Создать историческую базу знаний, которая на вопрос

> Что банк понимал под конкретной категорией на указанную дату?

возвращает:

- исходное название и описание категории банка;
- включённые и исключённые MCC;
- общебанковские исключения, при которых кешбэк не начисляется вообще;
- прочие ограничения, которые нельзя корректно выразить через MCC: СБП, QR, способ оплаты,
  подписка, минимальная сумма и другие условия;
- период действия правил, источник и степень полноты данных.

Этап 0 создаёт данные и API для чтения. Он **не** выбирает карту, не распределяет категории и
не импортирует историю транзакций. Эти сценарии используют готовую базу на следующих этапах.

Во всём коде и интерфейсе следует использовать термин **MCC** (`Merchant Category Code`), а
сам код хранить строкой из четырёх цифр, чтобы не терять ведущие нули.

## Главные решения

### 1. Разделить справочник MCC и трактовку банка

MCC — общий четырёхзначный код. При этом категории кешбэка, состав MCC и исключения являются
правилами конкретного банка, программы и периода. Поэтому каноническое описание MCC нельзя
смешивать с банковской категорией.

### 2. Хранить полную историю неизменяемыми ревизиями

У каждой ревизии правил нужны два независимых времени:

- `valid_from` / `valid_to` — когда правило фактически действовало у банка;
- `recorded_at` / `superseded_at` — когда CashFlow узнал об этой версии и когда заменил её
  следующей записью.

Границы периода задаются как `[valid_from, valid_to)`: начало включительно, конец не
включительно. Если банк не сообщил дату начала, она остаётся оценочной и сопровождается
признаком `validity_confidence`; нельзя молча выдавать дату обнаружения за официальную дату
начала действия.

Повторное получение тех же данных не создаёт новую ревизию: обновляется только `last_seen_at`.
Изменение нормализованного содержимого создаёт новую ревизию и закрывает предыдущую. Благодаря
этому можно восстановить как правила на дату покупки, так и сведения, которыми система
располагала в момент рекомендации.

### 3. Разделить области действия исключений

- `bank/program exclusion` — MCC или условие, при котором кешбэк не начисляется ни по одной
  категории данной программы;
- `category exclusion` — исключение только из конкретной повышенной категории;
- `category inclusion` — MCC, явно входящий в банковскую категорию;
- `text condition` — условие, которое пока нельзя безопасно нормализовать до MCC.

При будущем расчёте общепрограммный запрет имеет приоритет над включением в категорию, а
исключение категории — над её включением. На этапе 0 этот порядок уже фиксируется и покрывается
тестами, хотя рекомендательная логика ещё не реализуется.

### 4. Не считать название категории идентификатором

Название может меняться, а одинаковые названия могут означать разные наборы MCC. Стабильная
идентичность строится по `bank + program + source_external_id`. Если источник не предоставляет
ID, используется контролируемый `source_key`, а совпадение только по названию отправляется на
проверку и не склеивается автоматически при низкой уверенности.

### 5. Сохранять происхождение и исходный текст

Каждая опубликованная ревизия ссылается на снимок источника: URL, тип источника, время
получения, хеш содержимого и версию парсера. Исходный текст условий сохраняется без потерь.
Структурированные поля являются интерпретацией источника и всегда должны быть проверяемы по
снимку.

## Предлагаемая модель данных

Названия ниже рабочие; окончательные имена фиксируются в миграции и ADR.

```text
mcc_code
  code char(4) PK
  title
  description?
  reference_source?

bank_cashback_program
  id PK
  bank_id FK -> bank
  source_key
  name
  product_scope?          // вся программа, тариф или продукт
  UNIQUE(bank_id, source_key)

rule_source_snapshot
  id PK
  source_type             // public_page, pdf, api, browser, manual_verified
  source_url
  fetched_at
  published_at?
  content_hash
  raw_content?            // либо ссылка на защищённое объектное хранилище
  parser_name?
  parser_version?

bank_rule_revision
  id PK
  program_id FK
  valid_from
  valid_to?
  validity_confidence     // exact, inferred, unknown
  recorded_at
  superseded_at?
  source_snapshot_id FK
  completeness            // exact_mcc, partial_mcc, text_only, unknown
  status                  // draft, published, rejected
  normalized_hash

bank_category
  id PK
  program_id FK
  source_external_id?
  source_key
  created_at
  UNIQUE(program_id, source_key)

bank_category_revision
  id PK
  rule_revision_id FK
  bank_category_id FK
  original_name
  original_description?
  source_payload?

bank_category_mcc_rule
  category_revision_id FK
  mcc_code FK
  effect                  // include, exclude
  PRIMARY KEY(category_revision_id, mcc_code, effect)

bank_program_exclusion
  rule_revision_id FK
  mcc_code FK
  reason?
  PRIMARY KEY(rule_revision_id, mcc_code)

bank_rule_condition
  id PK
  rule_revision_id FK
  category_revision_id?   // NULL означает всю программу
  kind                    // payment_method, minimum_amount, subscription, other
  operator?
  value?
  original_text
```

`cashback_category` в текущем backend остаётся экземпляром предложения для конкретной карты и
месяца. На этапе 0 не следует превращать его в справочник. После стабилизации базы знаний в него
можно добавить nullable-ссылку на `bank_category_revision`: это свяжет текущий импорт с
банковским определением, не смешивая пользовательский выбор и публичные правила.

Для PostgreSQL стоит добавить индексы по `(program_id, valid_from, valid_to)`, MCC и
`normalized_hash`. Запрет пересекающихся опубликованных периодов для одной логической версии
нужно обеспечить ограничением PostgreSQL либо одинаковой транзакционной проверкой в сервисном
слое, совместимой с SQLite в разработке.

## Контракт данных

Текущий `CashbackImportDocument` версии 1 сохраняет MCC внутри `subtitle` или `description`, а
backend затем обрабатывает их как текст. Это теряет структуру и не подходит для истории правил.

Нужен отдельный версионируемый контракт снимка правил, например:

```json
{
  "schemaVersion": 1,
  "kind": "bank_mcc_rules_snapshot",
  "bankId": "tbank",
  "programKey": "default_cashback",
  "collectedAt": "2026-09-09T00:00:00Z",
  "source": {
    "type": "public_page",
    "url": "https://example.invalid/rules"
  },
  "validity": {
    "from": "2026-09-01",
    "to": "2026-10-01",
    "confidence": "exact"
  },
  "globalExcludedMcc": ["4829"],
  "conditions": [],
  "categories": [
    {
      "sourceId": "active-rest",
      "name": "Активный отдых",
      "includedMcc": ["7941", "7997"],
      "excludedMcc": [],
      "description": "Исходный текст банка",
      "completeness": "exact_mcc"
    }
  ]
}
```

Снимок публичных правил не должен требовать `user_id` или `card_id`. Персональный импорт
доступных категорий остаётся отдельным процессом. Это особенно важно для обновления правил по
расписанию без входа в аккаунт пользователя.

## План реализации

### 0.1. Зафиксировать словарь и границы домена

1. Утвердить термины: MCC, банковская категория, программа кешбэка, глобальное исключение,
   исключение категории, текстовое условие, снимок и ревизия.
2. Определить, различаются ли правила внутри одного банка по продукту/тарифу. Даже если первый
   источник общий, оставить `bank_cashback_program`, чтобы не привязывать правила напрямую к
   банку или карте.
3. Зафиксировать приоритет правил и поведение при неизвестных/частичных данных.
4. Оформить решения об истории, идентичности категории и доверии источникам короткими ADR.

Результат: согласованная ER-диаграмма, примеры запросов и правила разрешения конфликтов.

### 0.2. Создать схему и доменный сервис

1. Добавить Alembic-миграцию с таблицами и индексами.
2. Добавить SQLAlchemy-модели отдельно от текущего `CashbackCategory`.
3. Реализовать единый resolver с параметрами `bank/program/category/mcc/as_of/known_at`.
4. Валидировать MCC регулярным выражением `^[0-9]{4}$`, периоды и ссылки на справочник.
5. Реализовать идемпотентную запись снимка по хешу нормализованного содержимого.

Результат: база хранит несколько версий одних правил и детерминированно возвращает нужную.

### 0.3. Реализовать staging и публикацию

1. Любой импорт сначала создаёт `draft` и отчёт валидации.
2. Проверять неизвестные MCC, дубликаты, пересечение include/exclude, пустые категории,
   пересекающиеся периоды и резкое исчезновение большого числа правил.
3. Публиковать ревизию только целиком в одной транзакции; ошибка одной категории не должна
   оставлять частично обновлённый банк.
4. Разрешить ручную проверку и отклонение снимка с причиной.
5. Не удалять предыдущие версии при исправлении ошибки; создавать корректирующую ревизию.

Результат: сломанный парсер или изменившаяся страница банка не портят действующие данные.

### 0.4. Подключить источники

1. Начать с одного банка, где есть стабильный структурированный источник и MCC; текущий адаптер
   Т‑Банка уже получает `mccCodes` из ответа API и подходит как пилот.
2. Вынести `includedMcc` и `excludedMcc` в типизированные поля адаптеров вместо строки `MCC:` в
   `subtitle`/`description`.
3. Для банков, где доступен только текст или PDF, сохранять снимок и значение
   `completeness = text_only`; не угадывать полный перечень MCC.
4. Добавить адаптер общебанковских исключений отдельно от адаптера месячных персональных
   предложений.
5. Составить реестр источников: банк, программа, URL, формат, периодичность проверки, способ
   обнаружения изменений и ответственный парсер.

Результат: минимум один банк проходит полный путь источник → draft → проверка → публикация.

### 0.5. Добавить административное и read-only API

Минимальный набор:

- `POST /api/admin/mcc-rule-snapshots` — загрузить снимок в staging;
- `POST /api/admin/mcc-rule-revisions/{id}/publish` — опубликовать проверенную ревизию;
- `GET /api/admin/mcc-rule-revisions?bank_id=...` — получить черновики и историю для
  административного интерфейса;
- `POST /api/admin/banks/{bank_id}/mcc-rules/auto-import` — единая точка будущей
  автоматической загрузки (до подключения источника возвращает явный статус `not configured`);
- `GET /api/mcc/{code}` — получить справочное описание;
- `GET /api/banks/{bank_id}/mcc-rules?as_of=...&known_at=...` — правила банка на дату;
- `GET /api/banks/{bank_id}/categories/{category_id}/mcc-rules?as_of=...` — расшифровка
  категории;
- `GET /api/admin/mcc-rule-revisions/{id}/diff` — отличие от предыдущей версии.

Изменяющие endpoints доступны только роли `admin`; чтение можно оставить авторизованным ролям.
Ответы API обязательно содержат период, источник, `completeness` и предупреждения — не только
массив MCC.

Редкий ручной сценарий размещается в меню администратора как «Расширенные настройки MCC».
Экран позволяет выбрать банк, просмотреть опубликованные и черновые ревизии, создать правила с
нуля, сделать новую версию на основе существующей и опубликовать черновик. Редактирование
опубликованных данных напрямую запрещено: сохранение всегда создаёт новую ревизию.

### 0.6. Обновление по расписанию и наблюдаемость

1. Периодически проверять источники, но создавать ревизию только при изменении хеша.
2. Логировать запуск импорта, источник, версию парсера, число добавленных/удалённых правил и
   ошибки валидации.
3. Добавить сигналы: источник давно не проверялся, парсер вернул ноль категорий, MCC резко
   изменились, новая версия долго остаётся в draft.
4. Повторная обработка одного снимка должна быть безопасной и не создавать дублей.

Результат: обновления контролируемы, а устаревшие или подозрительные данные видны до того, как
их начнут использовать рекомендации.

### 0.7. Заполнить пилотные данные и принять этап

1. Загрузить официальный справочник MCC с зафиксированным источником и версией.
2. Загрузить минимум две последовательные ревизии правил пилотного банка, включая одну
   изменившуюся категорию.
3. Добавить второй банк с отличающимся составом MCC для категории с похожим названием.
4. Добавить пример глобального исключения и немаппируемого текстового ограничения (например,
   отсутствие кешбэка при оплате по СБП).
5. Проверить ответы на текущую и историческую даты.

## Тесты

- миграция вверх и вниз на чистой базе;
- валидация четырёхзначных MCC и сохранение ведущих нулей;
- идемпотентный повтор одного снимка;
- создание новой ревизии только при смысловом изменении;
- выбор версии на границах `[valid_from, valid_to)`;
- запрос с `known_at`, воспроизводящий знания системы в прошлом;
- запрет конфликтующих опубликованных периодов;
- приоритет глобального и категорийного исключений над включением;
- сохранение исходного текста и ссылки на снимок;
- атомарный rollback при ошибке импорта;
- contract-тесты JSON и fixture-тесты каждого банковского парсера;
- отсутствие регрессий в существующем `/api/cashback/import` версии 1.

## Критерии готовности этапа 0

Этап завершён, когда:

1. Для выбранного банка и даты API показывает банковские категории, включённые/исключённые MCC,
   глобальные исключения, источник и полноту данных.
2. Две версии правил доступны одновременно, а исторический запрос возвращает правильную.
3. Повторный импорт не создаёт дублей, а изменение источника создаёт проверяемый diff.
4. Частичные или только текстовые сведения явно помечены и не выдаются за полный список MCC.
5. Сбой парсинга не заменяет последнюю опубликованную версию пустыми данными.
6. Исходные банковские формулировки и снимки позволяют проверить любую нормализованную запись.
7. Есть хотя бы один глобальный запрет, одно исключение категории и одно условие не-MCC.
8. Текущий импорт категорий и Flutter-приложение продолжают работать без изменения контракта.

## Что оставить следующим этапам

- **Этап 1:** связать персональные предложения `cashback_category` с ревизиями правил и
  использовать MCC при выборе категорий и карты для оплаты.
- **Этап 2 (название/номер стоит зафиксировать):** импортировать банковские транзакции,
  нормализовать продавца и MCC, хранить пользовательские соответствия «продавец → наблюдаемый
  MCC» и предлагать карту для повторной покупки.

История транзакций не должна изменять официальный банковский справочник. Она станет отдельным
слоем наблюдений, который может повышать уверенность рекомендации и показывать, каким MCC
конкретный продавец фактически пользовался в прошлом.
