# Импорт и проверка MCC-ревизии

Статус: утверждено и реализовано во Flutter 22 сентября 2026 года на существующем контракте ревизий. Основной сценарий рассчитан на широкое окно и администратора; compact остаётся режимом сводки. Это вложенный маршрут `Ещё → Настройки MCC → Новый импорт`, а не самостоятельный раздел верхнего уровня.

Визуальный прототип: [desktop import review](design/concepts/mcc-import-review.png). Интерактивный HTML: [mcc-import-review.html](design/prototypes/mcc-import-review.html).

## Задача экрана

Безопасно провести администратора по цепочке:

**источник → файл/JSON → проверка → сводка и preview → draft → отдельная публикация**.

Главный принцип: импорт никогда не публикует данные автоматически. До создания draft пользователь видит, что распознано, что изменится и какие проблемы требуют решения. После создания draft публикация остаётся отдельным подтверждаемым действием. Опубликованная ревизия показывается как неизменяемая; исправление создаёт новую ревизию.

## Что действительно поддерживает backend

| Возможность | Состояние | Контракт |
| --- | --- | --- |
| Создать draft из JSON snapshot v1 | Реализовано | `POST /api/admin/mcc-rule-snapshots`, тело `{ "document": ... }` |
| Повторно передать тот же нормализованный набор | Реализовано | Возвращается существующая ревизия, обновляется `last_seen_at` |
| Проверить базовый формат и атомарно отклонить неверный snapshot | Реализовано | HTTP 400; draft не создаётся |
| Получить draft и историю банка | Реализовано | `GET /api/admin/mcc-rule-revisions?bank_id=...` |
| Опубликовать draft отдельно | Реализовано | `POST /api/admin/mcc-rule-revisions/{id}/publish` |
| Читать опубликованные правила на дату | Реализовано | `GET /api/banks/{id}/mcc-rules?as_of=...&known_at=...` |
| Автоматически загрузить правила банка | Не настроено | Явный `501 automatic_source_not_configured` |

Snapshot v1 принимает источники `public_page`, `pdf`, `api`, `browser`, `manual_verified`, но это метаданные происхождения. Наличие типа `pdf` или `public_page` не означает, что backend умеет получить и распарсить соответствующий файл или страницу.

Сервер сейчас проверяет, среди прочего:

- `schemaVersion: 1` и `kind: bank_mcc_rules_snapshot`;
- существование банка, обязательные ключ и название программы;
- период действия и допустимые значения уверенности/полноты;
- MCC как строки из четырёх цифр с сохранением ведущих нулей;
- уникальность `sourceKey` категорий;
- отсутствие одного MCC одновременно во включениях и исключениях категории;
- минимальную структуру текстовых условий.

## Предлагаемый desktop-процесс

### 1. Источник

Администратор выбирает банк и программу, затем способ ввода:

- **JSON snapshot v1** — рабочий путь текущего backend;
- файл PDF/CSV/XLSX — виден как будущий адаптер и помечен «парсер не подключён»;
- публичная страница/API — недоступны, пока источник банка не настроен;
- ручной редактор — запасной переход в существующий экран.

Для JSON показываются имя файла, размер, время выбора и checksum, если его вычисляет клиент. URL, дата публикации источника, имя и версия парсера относятся к происхождению, а не к доказательству качества данных.

### 2. Проверка

После чтения файла интерфейс показывает два уровня результата:

- блокирующие ошибки — draft нельзя создать;
- предупреждения — можно продолжить только после явного просмотра.

Ошибка всегда содержит путь/строку, причину и действие для исправления. Summary получает keyboard focus после неуспешной проверки, а каждая запись ведёт к соответствующему полю или строке. Цвет дублируется текстом и иконкой.

### 3. Сводка и preview

Перед созданием draft показываются:

- банк, программа, период, уверенность и полнота;
- число категорий, включённых и исключённых MCC, условий;
- сравнение с выбранной опубликованной ревизией;
- фильтруемый список `Добавлено / Изменено / Удалено / Без изменений`;
- происхождение и момент сбора данных;
- предупреждение о резком исчезновении правил или пустом наборе.

В строке preview сначала показывается смысловое изменение, затем конкретные MCC. Для больших списков полные значения раскрываются в detail-панели, а не растягивают таблицу.

### 4. Создание draft

Кнопка «Создать черновик» отправляет нормализованный snapshot. Во время запроса она блокируется и показывает прогресс. Ответы различаются:

- `201` — создан новый draft;
- `200` — такой нормализованный набор уже существует; показываются его id, статус и обновлённый `last_seen_at`;
- `400` — серверная ошибка контракта; сохраняется локальный preview и фокус переводится в error summary;
- `404` — банк не найден;
- сетевой сбой — файл и локальная проверка не сбрасываются, доступен повтор.

Draft не влияет на пользовательские ответы API до публикации.

### 5. Публикация

Публикация доступна только для существующего draft без блокирующих ошибок. Подтверждение повторяет банк, программу, период и величину изменения. Основная кнопка называется «Опубликовать ревизию», а не «Сохранить».

После успеха экран становится read-only и показывает `published_recorded_at`. Исправление начинается действием «Создать новую на основе этой», а не редактированием опубликованной версии.

## Адаптивная компоновка

Прототип использует общие runtime-пороги продукта, основанные на ширине окна:

- **широкий режим, от 840 px** — полный рабочий процесс импорта и публикации;
- **средний режим, 600–839 px** — read-only summary в широкой карточке; для редактирования предлагается открыть это же окно шире;
- **компактный режим, менее 600 px** — одноколоночный read-only summary без таблицы и форм.

В широком режиме:

- постоянная навигация продукта слева: только `Выгода · План · Акции · Ещё`; активен пункт «Ещё»;
- breadcrumb и возврат к истории ревизий показывают вложенность MCC-инструмента;
- компактный stepper и данные файла в левой колонке рабочего пространства;
- preview и список проблем в центральной широкой колонке;
- summary ревизии, provenance и действия в правой колонке;
- один основной CTA на текущем этапе;
- верхние фильтры остаются видимыми, но не перекрывают keyboard focus.

Preview — семантическая таблица с фиксированной шапкой только внутри страницы, без вложенной горизонтальной прокрутки при целевой desktop-ширине. Числа используют табличные цифры.

## Medium и compact fallback

При ширине менее 840 px импорт и публикация не предлагаются: это осознанный read-only fallback, а не урезанный редактор.

Показываются:

- статус последней проверки/draft/публикации;
- банк, программа, период и происхождение;
- четыре счётчика изменений;
- блокирующие ошибки и предупреждения карточками;
- действие «Открыть в широком окне» с локальной инструкцией увеличить ширину текущего окна и переход к существующей истории ревизий; межустройственная передача сеанса не подразумевается.

Причина недоступности сформулирована рядом с действиями. Никакие выбранные данные не должны теряться при изменении размера окна: если desktop-сеанс уже начат, compact-view сохраняет его summary и после возврата восстанавливает выбранный этап и фильтр.

## Состояния

1. Пустой: источник не выбран.
2. Файл читается: сохраняется размер области, показывается неблокирующий прогресс.
3. Проверка успешна: summary и preview доступны.
4. Есть предупреждения: draft возможен после просмотра.
5. Есть блокирующие ошибки: CTA создания draft недоступен, error summary сфокусирован.
6. Создание draft: повторный submit заблокирован.
7. Draft создан.
8. Идентичная ревизия найдена вместо создания новой.
9. Публикация требует подтверждения.
10. Опубликовано: неизменяемый read-only view.
11. Ошибка сети/сервера с повтором без сброса локального состояния.
12. Viewer или compact: read-only с явным объяснением ограничений.

## Backend gaps

Следующие элементы нужны целевому процессу, но сейчас отсутствуют. Прототип обозначает их как проектные возможности, а не готовое API:

- загрузка multipart-файла и хранение исходного бинарного файла;
- парсеры PDF/CSV/XLSX/публичных страниц и endpoint предварительного разбора;
- серверная построчная диагностика с координатами ошибок;
- endpoint preview/diff относительно выбранной ревизии;
- защита от публикации пустого набора и эвристика резкого исчезновения правил;
- запрет конфликтующих опубликованных периодов для всех вариантов `valid_from`;
- отклонение/архивация draft;
- серверный workflow подтверждения предупреждений и аудит автора действий;
- гарантированная неизменяемость опубликованных данных на уровне БД;
- настроенный auto-import хотя бы для одного банка;
- выдача raw source через отдельный безопасный endpoint.

До появления preview endpoint клиент может сравнивать уже полученные ревизии только для визуальной помощи. Такой diff не является серверной гарантией и не должен самостоятельно разрешать публикацию.

## Доступность и клавиатура

- логический порядок: заголовок → этапы → источник → error summary → preview → summary → CTA;
- все поля имеют видимые label и helper text;
- `Tab` проходит действия в визуальном порядке, `Enter/Space` активируют кнопки;
- фильтры изменений объявляют выбранное состояние;
- error summary использует `role="alert"`, доступен для focus и содержит ссылки на ошибки;
- status не передаётся одним цветом;
- focus ring имеет минимум 2 px и достаточный контраст;
- `prefers-reduced-motion` отключает декоративные переходы;
- при 200% масштабе текст переносится, действия не перекрывают содержимое.

## Решения для согласования

1. Оставляем ли medium/compact только для чтения или разрешаем на них публикацию уже созданного draft?
2. Должно ли подтверждение предупреждений сохраняться на сервере как аудит или достаточно локального состояния первой версии?
3. Какая опубликованная ревизия является базой diff: выбранная вручную, действующая на `valid_from` или последняя записанная?
4. Какие форматы получают первый реальный адаптер после JSON: CSV/XLSX или PDF?
5. Нужно ли вводить роль reviewer отдельно от admin перед подключением публикации?
