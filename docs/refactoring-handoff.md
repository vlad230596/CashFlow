# Рефакторинг: состояние и продолжение

Актуально на 15 октября 2026 года для локальной рабочей копии. Это техническая
очередь продолжения [анализа из 11 пунктов](refactoring-analysis-2026-10-14.md),
а не описание production. Изменения не развёрнуты. Проверять фактический diff

## Предлагаемый порядок следующей работы

Это порядок небольших технических изменений, не требование выполнить их
одновременно. Структурный долг сам по себе не означает критическую ошибку.

### 1. Завершить аудит асинхронного состояния

Точки входа: `app/lib/providers/data_provider.dart`, `api_client.dart`,
`test/provider_cache_test.dart`, `test/data_provider_test.dart`.

Проверить отдельные fetch/mutation методы, а не только fetchAllData: два ответа
в обратном порядке, logout/login во время запроса, смену даты, сохранение под
ключом другого аккаунта, старый откат после новой мутации. При извлечении stores
сохранить уже работающие guards. Критерий завершения — адресные регрессионные
тесты найденных пробелов; наличие session-aware транспорта само по себе недостаточно.

### 2. Выделять доменные stores за DataProvider

Точки входа: `reference_data_store.dart`, `mcc_repository.dart`, DataProvider.
Начать с одной области: подписки либо партнёрские предложения. Зафиксировать
владение состоянием, состояниями ошибки, кешем и версиями запросов. Определить,
когда обновление считается законченным при частичном отказе. Сейчас основные
коллекции применяются до подписок/акций, MCC обновляется без ожидания, но
fetchAllData всё ещё координирует последовательные этапы. Критерий — сохранённые
контракты фасада и независимое восстановление выбранной области после ошибки.

### 3. Извлекать backend без разрыва импортов

Точки входа: `backend/main.py`, `mcc_routes.py`, `migrations/env.py`,
`development_seed.py`, `conftest.py`. По одной границе выделять extensions/db,
модели, фабрику и маршруты; main временно сохраняет совместимые импорты.
Критерий — pytest, seed, Alembic upgrade/downgrade и прежняя WSGI-точка входа;
перед релизом также PostgreSQL/integration, которых текущая локальная проверка
не заменяет. Не вводить универсальный Repository для каждого ORM-запроса.

### 4. Завершить границы импорта

Точки входа: `app/lib/services/import_coordinator.dart`,
`app/browser_extension/adapters/extended/`, `contracts/cashback-amounts.v1.json`.
Отделить банковские scan/readDetail/open/close, оставляя DOM внутри адаптера.
Явно решить: независимые этапы или серверная атомарность; как распознаётся
повторный импорт и что пользователь повторяет после частичного успеха.
Критерий — повторный/частичный импорт без потери уже зафиксированного результата,
общие fixtures Python/TS и банковские адаптеры без общей DOM-эвристики.

### 5. Продолжить UI и типизацию после расчётных границ

Точки входа: `monthly_plan_projection.dart`, `plan_confirmation_screen.dart`,
`benefit_states_view.dart`, `card_context.dart`, модели банка/карты.
Выделить ConfirmationProjection и политику выбора, затем доказанные повторы
компонентов. Различать сохранённые сущности и DTO формы; не превращать nullable
поля в обязательные массовой заменой. Решение о сохранении локально изменяемого
лимита месячного плана остаётся открытым: серверное поле карты уже существует,
но UI-изменение лимита в плане ещё не сохраняется.

## Отдельные незакрытые вопросы MCC

- Холодный Web-запуск без сети: `app/web/cache_reset.js` удаляет service workers
  и CacheStorage. IndexedDB хранит данные, но оболочка сайта не доступна офлайн.
  Нужна политика обновления/восстановления PWA и проверка устаревшего приложения.
- Автоматический источник правил не подключён: 501 остаётся ожидаемым ответом.
- Preview-token защищает создание draft; для отложенной публикации отдельной
  гарантии актуальности сравнения пока нет. Не заявлять её существующей.
- HTTP 304 вычисляет fingerprint чтением данных; отдельного счётчика версии
  в БД и delta-синхронизации нет. Оптимизировать после измерений нагрузки.
- Бюджет 32 MiB относится к логическим записям; native recovery generations и
  IndexedDB имеют накладные расходы. Очистка после успешной записи намеренно
  допускает временный дополнительный объём. Проверять реальные квоты устройств.
- Для полного офлайн-справочника нужен успешный snapshot нового API. Сохранены
  чтение schema 1/2 и default schema 2 для старых клиентов; удалять совместимость
  только после отдельного решения о поддерживаемых версиях.

## Проверено и что ещё проверить перед поставкой

На локальном состоянии 15 октября: backend 142 теста и 8 subtests, Ruff,
lockfile, Alembic SQL; Flutter 167 тестов, analyze; Chrome 2 IndexedDB-теста;
Web release без CDN и Wasm dry-run. Дополнительно после защиты native reader
повторены 3 файловых теста. Расширение на первом этапе: typecheck, 82 Vitest и
production build. Подробности и Windows CanvasKit workaround — в отчёте MCC.

Не выполнены для этой поставки: полный Docker/PostgreSQL integration,
production migration/deploy, новая подписанная Android release-сборка и проверка
на целевом устройстве, живые банковские кабинеты. Это границы локальной проверки,
а не утверждение, что эти проверки падают. Миграция head — `0011_bank_identity`;
её SQLite upgrade/downgrade проверены, deployed revision не проверялась.

Из корня: `backend/.venv/Scripts/python.exe -m pytest -q`; из `app/` Flutter
запускать через `scripts/setup_vscode_flutter_env.ps1` согласно `app/AGENTS.md`.
Операции release/deploy и production-данные — только по правилам корневого
AGENTS.md и отдельному запросу пользователя. Не использовать локальную SQLite
для ответа о текущих данных.
