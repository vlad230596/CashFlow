## Информационная архитектура

Раздел не смешивает три разных объекта:

1. **Справочник** — канонический MCC-код, название, описание и источник.
2. **Правила банков** — трактовка кода конкретным банком, программой и категорией на выбранную дату.
3. **История версий** — административная работа с черновиками, публикациями и происхождением данных.

Текущий экран «Правила MCC» соответствует главным образом второму и третьему пунктам. В целевой структуре он становится частью общего раздела, а не единственной точкой входа.

## Основной мобильный сценарий

- Основной экран «Выгода» содержит единое поле «Что хотите купить?».
- Запрос можно задать на одном из трёх уровней: категория расходов, точный MCC-код или продавец.
- Автодополнение группирует результаты по типу и не заставляет пользователя заранее знать правильный уровень.
- Без поискового запроса под полем остаётся массовый просмотр категорий.
- После выбора экран показывает лучший вариант оплаты и альтернативы, не изменяя ручной план.
- Для запроса по продавцу можно раскрыть цепочку: история операций → вероятный MCC → категория банка → карта.

Пользовательский результат формулируется в контексте конкретной категории: «Подходит», «Не покрывает этот MCC» или «Нельзя проверить». Отсутствие MCC в частичном банковском списке не считается доказанным исключением.

Цепочка проверки: **операция → продавец → наблюдавшийся MCC → категория конкретного банка → карта**.

## Адаптивная структура

На телефоне это три состояния одного основного экрана «Выгода»: обзор категорий, смешанные поисковые подсказки и результат. Поле поиска остаётся доступным после выбора, а технические подробности раскрываются по запросу. Основная навигация остаётся «Выгода · План · Акции · Ещё».

На компьютере редкий административный сценарий ориентирован на импорт файла, предварительную проверку изменений и публикацию новой ревизии. Ручное редактирование остаётся запасным инструментом.

## Граница текущей реализации

Сейчас API умеет получать один MCC по точному коду, а модели операций и профиля MCC продавца ещё нет. Существующая сущность `PartnerMerchant` относится к партнёрским предложениям и не должна автоматически считаться продавцом из истории операций. Для целевого сценария потребуются импорт операций, нормализация продавцов, хранение наблюдений MCC и агрегированная проверка категорий. Макет не означает, что эти механики уже реализованы.
