# Исследование офлайн-кеша MCC

14 октября 2026 года. Независимый сабагент проверил реализацию; основной агент сравнил варианты хранения и выполнил воспроизводимый синтетический бенчмарк. Production не опрашивался. Код приложения в рамках исследования не изменялся.

## Вывод

Текущий компактный schema 2 существенно лучше исходного раздувания JSON, но это промежуточное решение. Основные проблемы — корректность обновления кеша, порядок чтения сети/диска, использование SharedPreferences для большого документа и предварительный расчёт всех ответов. Сначала стоит исправить жизненный цикл кеша, затем выбирать формат и хранилище. Перенос банковской логики в Dart только ради экономии десятков килобайт после gzip не оправдан.

## Воспроизводимый замер

Команда из корня:

```powershell
.\backend\.venv\Scripts\python.exe docs/research/mcc-offline-cache/benchmark.py
```

Скрипт принудительно устанавливает `CASHFLOW_DATABASE_URL=sqlite://` и `CASHFLOW_ENVIRONMENT=test` до импорта Flask. Все таблицы и данные создаются в памяти. Источники: bundled справочник, шесть файлов правил; по 112 синтетических предложений на банк, распределённых между шестью картами. Всего 1105 MCC, 6 программ, 672 предложения.

Это новый набор с явно заданным распределением предложений. Он отличается от прежнего одноразового замера 16,48/1,07 МБ: одинаковые агрегатные количества не означают одинаковую кратность повторения категорий/условий. Здесь исходный expanded JSON составляет 27,95 МБ. Сравнение вариантов ниже выполняется на одном и том же новом наборе.

Размеры в десятичных байтах; gzip level 6, UTF-8 JSON без лишних пробелов. Gzip здесь измерен локально, а не по реальной сети.

| Представление | JSON UTF-8 | gzip | Base64 от gzip, если хранить строкой |
|---|---:|---:|---:|
| Полные ответы для каждого MCC/предложения | 27 952 000 | 944 460 | 1 259 280 символов |
| Текущий schema 2 с вложенными `$ref` | 1 295 919 | 166 220 | 221 628 символов |
| Каталог + ревизии + предложения, без готовых ответов | 842 745 | 102 580 | 136 776 символов |
| Те же ревизии + готовый индекс статусов/ID | 1 430 477 | 116 109 | 154 812 символов |

Последний вариант использует обычные доменные идентификаторы: ревизия, категория, предложение. Он сохраняет серверные решения и не требует повторять evaluator в Dart. Сырой JSON больше нынешнего schema 2, но стандартное сжатие уменьшает его сильнее. Это пример того, почему один размер несжатого JSON не определяет лучший формат.

Сравнение семантики: для всех 1105 MCC прототип локального вычисления и прототип готового индекса восстановили те же bank verdicts и `offer_ids`, что текущий API на той же дате. Это проверка Python-прототипа; Dart-перенос, будущие даты и полная эквивалентность всех detail/API полей не проверены.

Медианы трёх прогонов на этом workstation:

- Построение expanded-представления: 1129 мс; дополнительная универсальная дедупликация: 513 мс. Текущая сборка снимка суммарно около 1,64 с до JSON serialization.
- Сборка нормализованного набора с загрузкой ревизий/предложений: 79 мс.
- JSON parse: текущий компактный набор 7,5 мс, нормализованный 3,7 мс, набор с индексом 10,6 мс.
- Одна оценка MCC 5411 по шести банкам в Python: медиана 0,94 мс (20 повторов).

Это не показатели Android/Flutter Web, не сетевые задержки и не замер памяти процесса. Особенно нельзя считать Python lookup оценкой Dart latency. Прототип индекса строился из expanded baseline, поэтому его полное server build-time не сравнивается.

Масштабный второй прогон, 1482 предложения: expanded 67,18 МБ; schema 2 1,313 МБ / gzip 170 КБ; нормализованные ревизии 1,016 МБ / gzip 109 КБ. Результаты сохранены отдельно. Скрипт по умолчанию воспроизводит основной набор 672; большая запись относится к исследовательскому предыдущему варианту генератора.

## Найденные дефекты и издержки

### Полный снимок теряется после частичного успешного обновления — подтверждено тестом

`app/lib/providers/data_provider.dart:604` заменяет снимок другой даты объектом schema 1 с одним ответом. `_loadMccCache()` на строке 499 затем считает сегодняшнее состояние уже загруженным.

Независимый временный Flutter-тест воспроизвёл:

1. Полный вчерашний снимок содержит 5814 и 7011; офлайн 7011 работает.
2. Сегодня онлайн успешно проверен только 5814.
3. Интернет исчезает; проверка 7011 бросает ClientException.
4. Вчерашний полный снимок всё ещё лежит на диске, но больше не используется.

Тест прошёл, ожидая этот дефект, затем был удалён. Это не утверждение, что проблема исправлена. Нужны неизменяемый полный базовый снимок и отдельные небольшие уточнения по кодам/датам, с fallback к базе для отсутствующего уточнения.

### Эвикция до подтверждения записи

`app/lib/services/mcc_cache_store.dart:103` удаляет старые снимки/указатели до `setString()` на строке 123. При ошибке квоты можно удалить последнюю рабочую офлайн-копию, не сохранив замену. Этот вывод установлен по коду; отказ настоящего browser storage не воспроизводился.

Нужна транзакция хранения либо запись новой версии, проверка и атомарное переключение указателя. При недостатке места нельзя обещать безопасную замену через две независимые записи localStorage; надо сохранять рабочую базу и возвращать явный результат неудачного обновления.

### Поиск зависит от сети раньше, чем от кеша

`data_provider.dart:588` сначала ждёт HTTP (до 5 секунд), только после ошибки возвращает сохранённый результат. Следует сразу отдавать локальную копию с датой, затем обновлять в фоне. Такую организацию чтения описывает [официальное руководство Flutter offline-first](https://docs.flutter.dev/app-architecture/design-patterns/offline-first).

### Один мегабайтный документ переписывается на каждый код

Индивидуальный successful lookup добавляет полный ответ поверх компактного набора и сериализует весь снимок (`data_provider.dart:634`). Это увеличивает записи и повторение данных. Уточнения лучше хранить отдельными записями/маленьким overlay, с версией правил и датой применимости.

### История и несколько учётных записей ограничены искусственным бюджетом

Бюджет MCC 1 500 000 UTF-16 code units глобальный. Ранее измеренный снимок 809 383 units и текущий новый 1 014 453 units означают, что два таких полных снимка в бюджет не помещаются. «Максимум три» — потолок количества, а не гарантия трёх дней/аккаунтов. Другие ключи приложения также занимают localStorage.

### Снимок смешивает данные разной изменчивости

Справочник и опубликованные банковские ревизии меняются иначе, чем выбор категорий и предложения на картах. Сохранённые `offer_ids` устаревают при изменениях в тех же сутках; проверки даты и аккаунта недостаточно. Нужна отдельная версия/инвалидация личного набора и связей с категориями.

### Компактный результат строится через большой промежуточный

`backend/main.py:2920` сначала вычисляет все ответы и детали всех предложений, включая исторические, затем `compact_snapshot()` ищет одинаковые JSON-поддеревья. Маленький итоговый файл не устраняет работу и промежуточные объекты. Лучше строить нормализованные сущности/индекс непосредственно; если evaluator остаётся на сервере, cache его вывод по версиям правил.

### Отсутствует дешёвая проверка изменений

Endpoint каждый раз строит снимок заново. В manifest можно вернуть версии каталога, ревизий и личных предложений; получать только изменившиеся части. [ETag и conditional requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/ETag) уменьшают повторную передачу. Но вычисление ETag после полной дорогой сборки сэкономит трафик, а не CPU: версию надо получать до построения ответа. `generated_at` не должен определять identity содержимого.

## Сравнение подходов

| Вариант | Преимущества | Цена/ограничения | Оценка для CashFlow |
|---|---|---|---|
| Нынешний schema 2 + SharedPreferences | Уже реализован, сервер владеет семантикой, быстрый доступ к готовому verdict | Собственный codec, общий лимит, целиком переписываемый JSON, ошибки lifecycle | Допустим как переходный после исправления дефектов |
| Schema 2 + gzip + корректный snapshot/overlay repository | Около 166 КБ binary на основном наборе, небольшая смена текущего протокола | Декомпрессия, версия packed-format, всё ещё собственные ссылки | Малый риск и быстрая экономия места; не заменяет исправление lifecycle |
| Нормализованные ревизии + локальная оценка | Наименьший measured размер, независимость от количества готовых запросов и даты | Второй evaluator в Dart, тесты семантической эквивалентности, versioned rules policy | Перспективно при развитии рекомендаций; не первый шаг только ради размера |
| Нормализованные ревизии + серверный индекс MCC | Простые ссылки на реальные сущности; сервер решает исключения; около 116 КБ gzip | Новый API/reader, отдельно обновляемые связи предложений | Предпочтительная цель без дублирования банковского evaluator |
| SQLite/Drift как единое хранилище | Транзакции, индексы, ревизии и incremental updates | Web wasm/worker, CSP/headers/compatibility, migrations | Разумно для дальнейшего общего local domain store; сейчас может быть лишним |

## Выбор хранилища

[shared_preferences](https://pub.dev/packages/shared_preferences) предназначен для простых значений; Web-реализация использует LocalStorage. [Web Storage](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API) синхронный, поэтому крупные JSON-записи занимают основной поток. Кеш восстановим с сервера, но именно его сохранность нужна пользователю при отсутствии сети.

Для Web предпочтителен [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API): асинхронное структурированное хранение и транзакции, binary blobs без Base64. В нативном приложении на этапе snapshots достаточно атомарной записи файла; SQLite нужен, когда появляются независимые записи, индексы и частые частичные обновления. Одинаковый repository-интерфейс может скрывать платформенные реализации.

[Квоты и eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) всё равно требуют обработки; IndexedDB не означает бесконечное или неуничтожаемое хранение. Можно проверять estimate и persistent-storage поддержку, показывать готовность offline набора. Секреты сессии остаются в secure storage; offline cache не отменяет авторизацию/изоляцию аккаунтов.

[Drift поддерживает Web](https://drift.simonbinder.eu/platforms/web/) через SQLite WASM и worker с несколькими persistence modes. Это viable аналог, но выбор следует проверять на наших целевых Chrome/Android/Safari, текущем CSP и нескольких вкладках. На нынешнем масштабе IndexedDB для snapshots проще, чем переход всей системы на SQLite WASM.

## Сжатие: передача и хранение — разные этапы

В repository примерах Caddy уже указан `encode zstd gzip` (`deploy/Caddyfile.cashflow.example:4`, dev example:2). [Caddy выбирает encoding по Accept-Encoding](https://caddyserver.com/docs/caddyfile/directives/encode). Развёрнутую конфигурацию и сетевой ответ production мы не проверяли: нельзя выдавать несжатые Flask serialization bytes за измеренный сетевой трафик.

HTTP compression обычно распаковывается до `json.decode()`. Поэтому gzip на Caddy сам по себе не уменьшает JSON-строку в SharedPreferences. Для диска/IndexedDB нужно отдельно сохранить сжатые bytes и распаковать при загрузке. Web имеет [Compression Streams API](https://developer.mozilla.org/en-US/docs/Web/API/Compression_Streams_API); в Dart есть [archive](https://pub.dev/packages/archive). Их реальные скорость/поддержка на целевых устройствах здесь не профилировались.

MessagePack/CBOR/bitset для четырёхзначных MCC тоже возможны, но переход на binary protocol не решит ошибки кеша или повторение предметных данных. Для примерно тысячи MCC сначала следует использовать нормализацию, готовые индексы и стандартное сжатие; оправданность другого encoding подтверждается отдельным замером.

## Рекомендуемая последовательность

1. Исправить потерю полного снимка и эвикцию до успешной записи; отдельный regression suite для нового дня, quota failure, смены аккаунта и конкурентных updates.
2. Читать локальный результат первым, обновлять в фоне; обновлять полную базу отдельно от main refresh и отдельно от частичных ответов.
3. Выделить MCC repository со стабильной базой, версиями/manifest и небольшими per-code overlays. Отделить опубликованные правила от личных связей предложений; добавить их инвалидацию.
4. Перенести крупный кеш в IndexedDB/native file или локальную БД. Добавить стандартное сжатие, если сравнение на реальных устройствах оправдывает CPU/размер; не считать HTTP compression дисковым.
5. Для постоянной архитектуры выбрать нормализованные ревизии + серверный индекс. Локальный evaluator вводить только с общими golden cases и доказанной эквивалентностью для всех исключений, нескольких программ, календарных границ и исторических ревизий.

Дополнительные результаты и исходники: `results.json`, `results-1482-offers.json`, `benchmark.py`. Исследование выявляет проблемы и предлагает следующие изменения; оно не заявляет, что перечисленные дефекты уже устранены.
