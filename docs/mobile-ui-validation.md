# Проверка мобильного интерфейса без Android-эмулятора

Актуально на 25 сентября 2026 года.

Android-эмулятор не нужен для каждой проверки интерфейса CashFlow. Большую
часть работы над адаптивной компоновкой можно выполнять в браузере и в
widget-тестах. Эмулятор остаётся контрольной средой для поведения, зависящего
от Android.

## Рекомендуемый цикл разработки

### 1. Быстрый интерактивный просмотр в Chrome

Из каталога `app/` запустить:

```powershell
.\scripts\setup_vscode_flutter_env.ps1 -Run "flutter run -d chrome"
```

Также можно использовать конфигурацию VS Code `CashFlow Frontend (Chrome)`.
В Chrome DevTools следует включить Device Toolbar и задать требуемый viewport,
например `390 × 844`, `375 × 812` или `360 × 800` логических пикселей.

Этот режим подходит для проверки:

- compact, medium и expanded-компоновки;
- переполнений, отступов и переноса текста;
- изменения интерфейса при изменении ширины окна;
- основных пользовательских переходов, не зависящих от нативной платформы.

Размер viewport — это размер области компоновки, а не обязательно физическое
разрешение экрана телефона. Для оценки адаптивности важнее логический размер;
плотность пикселей нужно проверять отдельно, если от неё зависят изображения
или отрисовка.

### 2. Widget-тесты на фиксированных размерах

Для воспроизводимой проверки задавать размер непосредственно в тесте:

```dart
tester.view.physicalSize = const Size(390, 844);
tester.view.devicePixelRatio = 1;
addTearDown(tester.view.resetPhysicalSize);
addTearDown(tester.view.resetDevicePixelRatio);
```

Допустим и существующий в проекте вариант:

```dart
await tester.binding.setSurfaceSize(const Size(360, 720));
addTearDown(() => tester.binding.setSurfaceSize(null));
```

В тестах CashFlow уже используются compact- и expanded-размеры. Новые
адаптивные экраны следует как минимум проверять на ширинах по обе стороны от
проектных границ:

- compact: меньше `600`;
- medium: `600–839`;
- expanded: `840` и больше.

Если важна стабильность внешнего вида, поверх такого теста можно добавить
golden-снимок. Обычные структурные widget-тесты следует сохранять даже при
наличии golden-проверки: они обычно менее чувствительны к несущественным
изменениям рендеринга.

### 3. Flutter Widget Previewer

В установленном SDK Flutter 3.41.8 доступна команда:

```powershell
.\scripts\setup_vscode_flutter_env.ps1 -Run "flutter widget-preview start"
```

Previewer позволяет помечать отдельные компоненты аннотацией `@Preview` и
указывать искусственный размер через `Size`. Это удобно для изолированной
разработки небольших виджетов. Для экранов CashFlow потребуется wrapper,
который предоставляет `MaterialApp`, тему и `DataProvider` либо тестовые
данные.

В Flutter 3.41 этот механизм следует считать дополнительным: официально
стабильным Widget Previewer объявлен начиная с Flutter 3.47. До обновления SDK
он не должен быть единственным способом проверки.

## Когда Android-эмулятор всё-таки обязателен

Перед выпуском и при изменении платформенного поведения нужно проверить
Android-сборку в эмуляторе или на реальном устройстве. Это требуется для:

- системных панелей, safe area и экранной клавиатуры;
- Android-навигации, кнопки Back, жестов и touch-поведения;
- разрешений и нативных плагинов;
- платформенных шрифтов и отличий нативного рендеринга;
- запуска, производительности и поведения release-сборки.

## Практическое решение для CashFlow

Для повседневной UI-разработки использовать Chrome с заданным viewport и
widget-тесты на контрольных ширинах. Android-эмулятор запускать для финальной
проверки ключевых сценариев и всех изменений, затрагивающих нативное
поведение. Простое изменение размера desktop-окна допустимо как быстрая
проверка, но не заменяет ни мобильный viewport, ни Android-проверку.
