# CashFlow: вход, системные состояния и административные экраны

Статус: утверждено и реализовано во Flutter 22 сентября 2026 года на существующих backend-контрактах.

Артефакты:

- воспроизводимый storyboard: `docs/design/prototypes/admin-access-views.html`;
- PNG-лист: `docs/design/concepts/admin-access-views.png`.

## 1. Проверенная основа в коде

У приложения уже есть серверная bearer-сессия, закрытая регистрация и три иерархические роли. Аккаунт для входа (`AuthUser`) и участник семьи — владелец карт (`UserModel`) являются разными сущностями.

| Возможность | viewer | editor | admin |
| --- | --- | --- | --- |
| Читать банки, участников, карты, кешбэк и правила | да | да | да |
| Менять кешбэк-категории и запускать существующий импорт кешбэка | нет | да | да |
| Менять банки, участников-владельцев и карты | нет | нет | да |
| Читать/создавать/публиковать MCC-ревизии | нет | нет | да |
| Управлять аккаунтами входа | нет | нет | да, backend API существует, Flutter UI пока отсутствует |

Источники истины: `backend/AUTHENTICATION.md`, `_required_role()` в `backend/main.py`, `canEdit` и `isAdmin` в `app/lib/providers/data_provider.dart`.

Прототип не добавляет регистрацию, восстановление пароля, приглашения, смену собственного пароля, удаление аккаунтов входа, bulk-операции или новые источники MCC. Они отсутствуют в проверенном контракте.

## 2. Информационная архитектура

Служебные данные не становятся новой основной вкладкой. Точка входа находится в «Ещё» и называется **«Управление»**.

- Viewer: видит обычный продукт. Если открыл административный deep link, получает состояние «Недостаточно прав» с возвратом в «Выгоду».
- Editor: видит импорт кешбэка там, где он уже уместен, но не административный hub.
- Admin: видит hub и разделы «Банки», «Участники», «Карты», «Правила MCC». Управление аккаунтами входа фиксируется как отдельная будущая view, но не смешивается с участниками семьи.

Runtime-контракт для будущей Flutter-реализации:

- compact, `<600 dp`: верхняя панель, карточный список, создание и редактирование отдельным экраном;
- medium, `600–839 dp`: одна основная колонка с ограничением ширины; допустимы двухколоночные группы коротких полей;
- expanded, `>=840 dp`: постоянный rail, таблица и detail/form рядом.

Сам HTML — storyboard-лист с несколькими подписанными device frames, а не готовая runtime shell. Его внешняя сетка лишь перекладывает frames на этих же порогах; фактическую адаптацию Flutter следует тестировать через `LayoutBuilder` по ширине окна, а не устройства.

## 3. Вход

### Состав

- логотип/название и короткое обещание продукта;
- видимые labels «Логин» и «Пароль»;
- show/hide password с доступным названием;
- primary action «Войти», блокируемый во время запроса;
- нейтральное пояснение «Доступ выдаёт администратор» вместо несуществующей регистрации;
- диагностическая строка сервера — только в раскрываемых технических деталях, не в основном потоке.

### Состояния

- Начальное: autofill и paste разрешены.
- Отправка: индикатор внутри кнопки, поля сохраняют значения, повторная отправка заблокирована.
- Ошибка 401: единое сообщение «Неверный логин или пароль» без раскрытия существования аккаунта.
- Ошибка 429: «Слишком много попыток. Повторите через 15 минут»; поля остаются доступны, кнопка может показывать время ожидания.
- Сеть недоступна до первой подтверждённой сессии: понятное offline-сообщение и «Повторить».
- Сохранённая ранее подтверждённая сессия: приложение открывает кешированные данные и показывает ненавязчивый offline banner. Это соответствует текущему клиенту.

## 4. Общие системные состояния

Все состояния занимают область содержимого, сохраняя оболочку и путь назад, кроме первого запуска/auth gate.

| Состояние | Подача | Действие |
| --- | --- | --- |
| Короткая загрузка | зарезервированный каркас строк/карточек | нет |
| Долгая загрузка | каркас + текст «Загружаем данные» | отмена только если операция реально отменяема |
| Ошибка загрузки | причина на человеческом языке, без stack trace | «Повторить» |
| Offline с кешем | компактный persistent banner, дата последнего обновления | «Обновить» |
| Offline без кеша | самостоятельная пустая view | «Повторить» |
| Нет прав | shield/lock icon, требуемая роль, безопасный выход | «Вернуться в Выгоду» |
| Пустой список | объяснение сущности и один primary CTA при наличии права | «Добавить…» только admin |

Ошибки формы показываются и в focusable summary сверху, и около конкретного поля. Toast/snackbar применяется только для результата успешного действия и не заменяет inline error.

## 5. Административный hub

Hub отвечает на два вопроса: «что я могу администрировать?» и «где требуется внимание?». Он не изображает несуществующую аналитику.

- четыре destination-card: банки, участники, карты, правила MCC;
- реальные локальные счётчики можно показывать для первых трёх;
- для MCC не обещать общий счётчик, пока нет агрегирующего endpoint: вместо него — «Выберите банк»;
- роль текущего аккаунта и server authority показываются в profile menu, а не как главный контент;
- действия создания находятся внутри соответствующего раздела, не на hub.

## 6. Унифицированный list pattern

Одинаковая структура уменьшает стоимость обучения:

1. title + count (только если count уже получен);
2. поиск по загруженному списку;
3. contextual filter при наличии (для MCC — банк и статус);
4. одна primary action «Добавить…»/«Новая ревизия»;
5. desktop table с кликабельной строкой и overflow-actions;
6. compact cards с теми же полями и явным chevron;
7. loading/error/empty внутри стабильной области списка.

Поля по сущностям:

- Банк: название, описание.
- Участник: имя. Не называть его «пользователем входа».
- Карта: последние 4 цифры, платёжная система, тип, банк, участник.
- MCC-ревизия: банк, программа, статус `draft/published`, период действия, полнота, источник, число категорий.

Viewer может использовать read-only list/detail только там, где этот служебный маршрут действительно открыт продуктовым решением. Editor не получает disabled admin CTA: действие отсутствует, а причина доступна через «О доступе». Admin видит mutation actions.

## 7. Унифицированный form pattern

- Заголовок явно различает создание и редактирование.
- Поля сгруппированы; labels не заменяются placeholder.
- На compact primary action находится в нижней safe-area панели, на desktop — вверху/внизу формы без дублирования tab order.
- При уходе с изменённой формы требуется подтверждение.
- Delete отделён в danger zone и подтверждается названием сущности.
- Во время сохранения кнопка блокируется, форма сохраняет введённое.
- После успеха — возврат к сохранённой строке и короткое announcement.

Существующие поля:

- банк: name, description;
- участник: name;
- карта: payment system, card type, last four digits, bank, participant;
- MCC snapshot: программа, product scope, период, confidence/completeness, источник, глобальные исключения, категории, их included/excluded MCC и conditions.

Для MCC опубликованная ревизия неизменяема: «Изменить» создаёт новую ревизию на её основе. Публикация доступна только черновику и требует подтверждения. Diff/preview до публикации обозначен как следующий UX-этап: backend сейчас не предоставляет отдельный diff-contract, поэтому прототип его не симулирует.

Endpoint auto-import сейчас отвечает `501 Not Implemented`. Поэтому он не является рабочим путём: в storyboard показан disabled control «Автоимпорт недоступен», а ручное создание ревизии остаётся единственным активным входом. Control нужен только как честная фиксация границы текущей системы; в production его допустимо полностью скрыть до реализации backend.

## 8. Визуальная гипотеза storyboard

Использован спокойный служебный слой: светлый фон, тёмно-синий текст, синий primary, янтарный только для черновика/внимания, красный только для ошибки/destructive. Это самостоятельная гипотеза для проверки и не переопределяет будущие product tokens.

- 4/8 px spacing rhythm;
- минимум 48 px для touch controls;
- текст от 16 px на compact views;
- focus ring 3 px;
- смысл статуса всегда передаётся текстом и icon, не одним цветом;
- motion только для причинных переходов, выключается через `prefers-reduced-motion`.

## 9. Что утвердить

1. Нужен ли viewer доступ к read-only справочникам через «Управление», или административный hub должен быть полностью скрыт от viewer/editor?
2. Подтверждаем ли термин «Участники» для `UserModel`, оставляя «Аккаунты доступа» для `AuthUser`?
3. Нужна ли Flutter-view управления аккаунтами входа в следующей итерации? Backend поддерживает list/create/update, но текущего экрана нет.
4. Подтверждаем ли публикацию MCC как admin-only операцию согласно текущему контракту?
5. Подходит ли split-view на desktop и full-screen форма на mobile как единый адаптивный pattern?

## 10. Граница реализации

Этот пакет покрывает UX и воспроизводимый HTML. Flutter production-код, backend, `product-design-status.md` и `CONTEXT.md` не изменялись. После утверждения следует отдельно описать маршруты, семантические widgets и тестовую матрицу ролей/ширин.

## 11. Визуальная проверка

Storyboard отрендерен локальным Chromium и проверен визуально:

- 1600 × 1000, full-page: итоговый PNG-лист;
- 375 × 812: compact reflow, одна колонка, без видимого горизонтального переполнения;
- 812 × 375: landscape reflow, без обрезанных form actions;
- `prefers-reduced-motion`: декоративное движение отсутствует, hover-transition включается только при разрешённом motion;
- структурные icons — inline SVG; emoji не используются;
- labels, focus ring, inline errors и текстовые статусы присутствуют;
- интерактивные controls спроектированы минимум 48 px по высоте/ширине; целевой Flutter минимум — 48 dp;
- формы и fixed actions в показанном compact-макете учитывают нижний `safe-area-inset`.

Ограничение проверки: storyboard фиксирует только светлую визуальную гипотезу. Dark theme, Dynamic Type/максимальный системный размер текста и реальный screen-reader порядок следует тестировать уже на Flutter-компонентах; их нельзя достоверно подтвердить статичным HTML-листом.
