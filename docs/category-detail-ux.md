# Карточка категории кешбэка

Статус: утверждено и реализовано во Flutter 22 сентября 2026 года без изменения production API. Интерактивный прототип: [category-detail.html](design/prototypes/category-detail.html), обзорный макет: [category-detail.png](design/concepts/category-detail.png).

Все банк, карта, владелец, даты и значения в макете демонстрационные.

## 1. Назначение и граница

Это detail конкретного предложения по конкретной карте, а не второй список «Выгода». Он отвечает на три вопроса:

1. какие условия банк сообщил для этой карты;
2. находится ли предложение в локальном плане;
3. подтверждена ли его фактическая активация банковским снимком.

Поиск, сравнение карт и вычисление «лучшей карты» остаются в «Выгоде». Управление набором назначений остаётся в «Плане». Detail может открыть соответствующий контекст, но не повторяет их каталоги.

## 2. Данные из текущего контракта

| В интерфейсе | Поле |
|---|---|
| Название | `name` |
| Процент | `cashback_percent` |
| Карта | `card_id` → уже загруженные `cards`, `banks`, `users` |
| Период | `start_date`, `end_date` |
| Условия | `description` |
| Лимит кешбэка | `max_cashback_amount` |
| Минимальная покупка | `min_purchase_amount` |
| Тип | `category_type` |
| В локальном плане | `is_selected` |
| Выбор зафиксирован банком | `is_selection_locked` |
| Подтверждено банковским снимком | `is_bank_confirmed` |

Типы отображаются человеческими формулировками, но сохраняются без переименования:

- `standard` → «Обычная»: расходует место выбора и может переключаться в плане, если выбор не зафиксирован;
- `stackable_bonus` → «Дополнительная»: суммируется и не расходует лимит обычных категорий;
- `task_bonus` → «За задание»: бонус связан с выполнением банковского условия и не является обычным местом выбора.

## 3. Иерархия detail

### Сводка

Верхняя карточка всегда показывает название, процент, банк/карту, владельца и период. Рядом находятся три независимые текстовые метки:

- тип предложения;
- «В плане» / «Не в плане»;
- «Подтверждено банком» / «Ждёт подтверждения».

Цвет только поддерживает текст и пиктограмму. Процент — главное числовое значение, но не обещание итоговой выгоды: рядом видны лимит и минимальная покупка, если они известны.

### Условия

Показываются только реально сохранённые сведения: описание, максимальный кешбэк и минимальная сумма покупки. Пустое nullable-поле выводится как «Банк не указал», а не как ноль. MCC, исключения, остаток лимита, источник импорта и время подтверждения не показываются: этих связей/полей у категории сейчас нет.

### План и подтверждение

Намерение и доказательство разнесены в две строки. `is_selected && is_bank_confirmed` означает действующую категорию. `is_selected && !is_bank_confirmed` — только намерение, ожидающее свежего банковского снимка. `is_selection_locked` блокирует изменение выбора и поясняется словами «Выбор зафиксирован банком».

Кнопка ручного банковского подтверждения отсутствует. Текущий API принимает доказательство через импорт; обычный `PUT /cashback/:id` не должен имитировать его создание.

## 4. Роли и режим редактирования

### Viewer

Viewer получает семантически read-only detail: обычный текст и карточки, а не серую отключённую форму. Кнопки сохранения и изменения плана отсутствуют. Небольшая подпись «Только просмотр» объясняет режим без навязчивого banner.

### Editor/admin

Detail сначала открывается в режиме чтения. Действие «Редактировать» раскрывает форму. Это защищает от случайного изменения банковских данных и оставляет основной сценарий быстрым.

Форма сгруппирована:

1. **Основное:** название, процент, тип, карта.
2. **Период:** дата начала и окончания.
3. **Условия:** описание, максимум кешбэка, минимальная покупка.
4. **План:** переключатель только для `standard` и только когда `is_selection_locked == false`.

ID остаётся технической подписью внизу и не занимает отдельное поле.

Если изменились `name`, даты, процент, `card_id` или `category_type`, перед сохранением показывается постоянное предупреждение: «Банковское подтверждение будет отозвано». Это соответствует backend: изменение банковских условий сбрасывает `is_bank_confirmed`. Изменение `is_selected` также отзывает подтверждение.

При выходе из формы с несохранёнными изменениями нужен confirm-dialog. Во время сохранения primary-кнопка блокируется и показывает progress; ошибка остаётся в форме с действием «Повторить».

## 5. Валидация

| Поле | Правило интерфейса |
|---|---|
| Название | обязательное, после trim не пустое; UI учитывает серверный предел модели 50 символов |
| Процент | обязательное конечное число; отрицательное значение и продуктовый верхний предел backend сейчас не валидирует — см. gaps |
| Карта | обязательная существующая карта |
| Начало/окончание | обе даты обязательны; окончание не раньше начала в календарном UX |
| Максимальный кешбэк | пусто или неотрицательное число |
| Минимальная покупка | пусто или неотрицательное число |
| Описание | необязательное, многострочное |

Ошибки появляются после blur или submit прямо под полем. При нескольких ошибках наверху появляется focusable summary со ссылками на поля; введённые значения не сбрасываются. Формат ввода принимает точку и запятую, а отображение валюты/дат локализуется.

Есть расхождение контракта дат: backend требует `start_date < end_date`, а текущий Flutter editor превращает окончание выбранного дня в `23:59:59.999`, поэтому один календарный день фактически допустим. Production-реализация должна сохранить эту нормализацию и тестировать именно отправляемые timestamps.

## 6. Адаптивность

- **Compact `<600`:** один поток; сводка → статусы → условия. Форма открывается отдельным состоянием этого же экрана, sticky CTA учитывает safe area и не перекрывает последнее поле.
- **Medium `600–839`:** один широкий поток с двухколоночными короткими полями; длинное описание остаётся на всю ширину.
- **Expanded `≥840`:** слева стабильный read-only summary, справа detail/форма. При переходе между ширинами черновик, выбранные даты и scroll position сохраняются.

Форма ограничивает ширину текста; поля не растягиваются на весь desktop. При 200% text scale метки переносятся, процент и статусы не накладываются.

## 7. Состояния

- загрузка: skeleton с теми же границами карточек, без прыжка компоновки;
- сохранение: поля остаются читаемыми, кнопка disabled + progress;
- ошибка загрузки без кеша: сообщение и «Повторить»;
- ошибка сохранения: общий recovery-banner и inline ошибки ответа, черновик сохранён;
- запись удалена/недоступна: нейтральное «Предложение больше недоступно» и возврат;
- карта из `card_id` не найдена локально: показывать «Карта недоступна · ID …», не подставлять другую карту;
- viewer: полный read-only контент без mutation controls.

## 8. Gaps текущего контракта

1. У подтверждения нет источника, автора и времени; detail может показать только boolean `is_bank_confirmed`.
2. Нет связи категории с MCC, исключениями оплаты, источником банковских данных или временем последней синхронизации.
3. Нет потраченной суммы и остатка `max_cashback_amount`; нельзя показывать progress лимита.
4. Backend не ограничивает допустимые `category_type`, процент и денежные значения. До server validation client обязан быть консервативным, но не может считаться границей доверия.
5. `updateCashbackCategory()` отправляет весь объект, включая `is_bank_confirmed`, хотя backend игнорирует ручную запись этого поля. Желателен отдельный update DTO с allowlist.
6. Текущий Flutter editor сводит любой не-`stackable_bonus` тип к `standard`, поэтому `task_bonus` может быть потерян при сохранении. Новый editor обязан поддерживать все три известных значения или делать неизвестный тип read-only.
7. Нет revision/version для защиты от одновременного редактирования.
8. Изменение `is_selected` из detail сознательно не предлагается: назначение категории остаётся ответственностью экрана «План».

## 9. Доступность и проверка реализации

- Flutter touch targets не меньше 48 dp, между соседними целями минимум 8 dp.
- Видимые labels и helper text; placeholder не заменяет label.
- Focus order: назад → заголовок → статусы → условия → «Редактировать» → поля → отмена/сохранение.
- Ошибка не кодируется только красным; status не кодируется только зелёным.
- Read-only не реализуется набором disabled input: screen reader получает текстовые значения.
- Sticky CTA не скрывает keyboard focus; back и system gesture ведут через проверку несохранённого черновика.
- Прототип проверяется на 375 px, desktop и landscape; reduced-motion отключает необязательные transitions. Dark mode и фактический Dynamic Type/TalkBack/VoiceOver проверяются при Flutter-реализации.

## 10. Что утвердить

1. Утверждено для макета: назначение «В плане» изменяется только на экране «План»; detail показывает статус и ссылку-переход.
2. Разрешаем ли менять `task_bonus`, или импортные task-записи должны быть полностью read-only?
3. Какие серверные диапазоны утверждаем для процента и денежных значений?
4. Нужен ли delete на этом экране? Сейчас он сознательно не показан: задача не запросила destructive flow, хотя endpoint существует.
