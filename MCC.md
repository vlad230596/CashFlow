# MCC в CashFlow: состояние, назначение и планы

Актуально по коду рабочего дерева на 5 октября 2026 года. Документ описывает механизм банковских
правил MCC; наличие файлов с правилами банков в репозитории не означает, что они уже загружены или
развёрнуты в production.

## Зачем это нужно

MCC (`Merchant Category Code`) — четырёхзначный код вида деятельности продавца. Банк определяет
по нему категорию операции, но банковская категория кешбэка **не равна** универсальной категории
MCC: банки по-разному группируют коды, исключают отдельные операции и меняют правила со временем.
Одно название вроде «Активный отдых» может означать разный набор кодов в разных банках.

Нам нужна проверяемая расшифровка: какие MCC банк включал в категорию, какие исключал, при каких
условиях кешбэк не начислялся вообще и **в какой период** всё это действовало. Это решает три
задачи:

1. Не сравнивать банковские категории только по похожим названиям.
2. В будущем выбирать категорию и карту для конкретной покупки с учётом MCC, исключений и даты.
3. Позже сопоставлять повторные покупки с наблюдаемым MCC из истории транзакций, не принимая
   пользовательские наблюдения за официальные правила банка.

Система должна явно различать «MCC неизвестен», «известен неполный список» и «известен полный
список». Отсутствие кода в неполном списке не означает, что код исключён. Один продавец также
может проводить разные операции под разными MCC.

## Что работает сейчас

### Хранение и API

- Подготовлена Alembic-миграция
  [`0003_mcc_rule_history.py`](backend/migrations/versions/0003_mcc_rule_history.py). Она создаёт
  справочник кодов, банковские программы, категории, снимки источников, исторические ревизии,
  включённые/исключённые MCC и условия. Миграция не применялась здесь к production.
- Реализованы модели и HTTP API в [`backend/main.py`](backend/main.py). MCC хранится строкой из
  четырёх цифр — ведущие нули не теряются. Миграция `0007_seed_mcc_catalog` заполняет справочник
  зафиксированным CSV-снимком mcc-codes.ru из 1 077 кодов и сохраняет URL источника. При ручной
  загрузке неизвестный код по-прежнему получает запись в `mcc_code` без названия.
- Отдельный JSON-контракт `bank_mcc_rules_snapshot` версии 1 позволяет создать черновую ревизию
  правил без привязки к пользователю или карте. Проверяются формат MCC, даты, ключи категорий и
  конфликт одновременного включения/исключения одного MCC внутри категории. Повторный снимок с
  тем же нормализованным содержимым не создаёт новую ревизию; обновляется `last_seen_at`.
- Публикация черновика выполняется отдельным запросом. Для опубликованных правил есть запрос по
  дате действия (`as_of`); дополнительный `known_at` позволяет восстановить, какая опубликованная
  версия была известна системе в прошлом. Запросы возвращают происхождение, полноту и состав
  правил, а не только список кодов.
- Изменяющие MCC endpoints и список административных ревизий доступны только роли `admin`.

Основные endpoints:

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/admin/mcc-rule-snapshots` | Создать черновик из JSON-снимка или найти существующую версию |
| `GET /api/admin/mcc-rule-revisions?bank_id=...` | Список черновиков и истории банка |
| `POST /api/admin/mcc-rule-revisions/{id}/publish` | Опубликовать черновик |
| `GET /api/banks/{id}/mcc-rules?as_of=...&known_at=...` | Правила банка на дату |
| `GET /api/banks/{id}/categories/{id}/mcc-rules?as_of=...` | Расшифровка одной категории |
| `GET /api/mcc/{code}` | Запись в справочнике MCC, если она есть |
| `POST /api/admin/banks/{id}/mcc-rules/auto-import` | Пока явный ответ `501 automatic_source_not_configured` |

### Интерфейс

Администратор открывает редкий сценарий через меню настроек → «Расширенные настройки MCC».
В [`mcc_rules_settings_screen.dart`](app/lib/screens/settings/mcc_rules_settings_screen.dart)
можно выбрать банк, увидеть черновики и опубликованные версии, глобальные исключения и MCC по
категориям. В
[`mcc_rule_edit_screen.dart`](app/lib/screens/settings/mcc_rule_edit_screen.dart) можно создать
набор с нуля либо взять существующую ревизию за основу, добавить/удалить категории, изменить
списки MCC, указать программу, даты, источник и полноту данных. Сохранение создаёт черновик;
публикация — отдельное действие. Опубликованная ревизия не редактируется «на месте».

Кнопка «Подгрузить автоматически» уже есть, но **реального источника за ней пока нет**. Нажатие
показывает, что автоматический импорт для банка не настроен; данные не меняются.

### Единые категории, исключения и данные банков (с 5 октября 2026)

- **Единые категории.** Миграция
  [`0010_canonical_categories.py`](backend/migrations/versions/0010_canonical_categories.py)
  добавляет 43 единые категории в 10 группах
  ([`canonical_categories.json`](backend/data/canonical_categories.json)): название, синонимы для
  поиска, приоритет потребности по умолчанию и ядро MCC. Исходное название банковской категории
  не меняется; связь с единой хранится в `bank_category_canonical_link` с отношением `exact`,
  `broader` (банк шире, покрывает несколько единых) или `narrower` и долей покрытия ядра.
- **Привязка по MCC, а не по названию.** При импорте связи считает
  [`canonical_categories.py`](backend/canonical_categories.py). Категории без MCC (сервисы банка,
  партнёры, «Самокаты» и т.п.) привязываются вручную полем `canonicalKeys`. Категории «Все
  покупки» не привязываются.
- **Тип категории**: `mcc`, `all_purchases`, `payment_method`, `bank_service`, `partner`, `other`.
- **Типы исключений.** У `bank_program_exclusion` появились `kind` и заполняемый `reason`:
  `always` — никогда; `unless_category` — только в выбранной категории, где код указан (ЖКХ и связь
  у ВТБ и Сбера); `conditional` — при условии (сервис, канал, сумма). Snapshot принимает массив
  `exclusions: [{mcc, kind, reason}]`; если код встречается в нескольких группах, побеждает более
  строгий тип. `global_excluded_mcc` в ответах содержит только `always`.
- **Проверка кода покупки.** `GET /api/mcc/{code}/bank-rules?as_of=` возвращает по каждому банку
  статус `category`, `category_only`, `conditional`, `excluded` или `not_in_categories`, найденные
  категории и исключение. `GET /api/canonical-categories` и
  `GET /api/canonical-categories/{key}/bank-categories?as_of=` дают поиск по единым категориям.
- **Данные шести банков** (Озон, Альфа, ВТБ, Т-Банк, Яндекс Пэй, Сбер) лежат в
  [`backend/data/bank_mcc_rules/2026-10`](backend/data/bank_mcc_rules/2026-10) и загружаются
  командой `flask --app main import-bank-mcc-rules` или через экран «Новый импорт». Это ручная
  расшифровка документов банков; противоречия документов сохранены как условия. Описание
  источников — в [`backend/data/README.md`](backend/data/README.md).

Персональные месячные предложения по картам (`/api/cashback/import`) хранятся отдельно, но с
5 октября 2026 года каждое приходит с полем `canonical_keys`. Сервер берёт связи категории банка с
тем же названием из опубликованных правил (точный путь, по MCC), а если её нет — подсказку по
названию (`canonical_categories.resolve_canonical_by_name`). Экран плана группирует предложения
по единым категориям: широкое предложение банка закрывает сразу несколько потребностей. Поиск
учитывает синонимы. Брендовые предложения и «Все покупки» связей не получают и группируются по
названию, как раньше.

## Как механизм устроен технически

```text
bank
  └─ bank_cashback_program              программа/тариф банка
       ├─ bank_category                 стабильный source_key категории
       └─ bank_rule_revision            версия правил и срок действия
            ├─ rule_source_snapshot     происхождение и полученный JSON
            ├─ bank_program_exclusion   исключения MCC: always / unless_category / conditional
            ├─ bank_rule_condition      условия программы или категории
            └─ bank_category_revision   название/описание и тип в этой версии
                 ├─ bank_category_mcc_rule (include / exclude)
                 └─ bank_category_canonical_link → canonical_category

mcc_code                               общий справочник четырёхзначных кодов
canonical_category (+ canonical_category_mcc)  единые категории и их ядро MCC
cashback_category                      отдельные предложения конкретной карты/месяца
```

Снимок проходит цепочку: **источник или ручной ввод → проверка и нормализация → `draft` →
публикация → чтение по дате**. Нормализованное содержимое хешируется для идемпотентности;
исходный полученный JSON тоже сохраняется с хешем и метаданными источника. Сейчас это именно
JSON, переданный в API, а не гарантированная копия публичной веб-страницы или PDF.

У ревизии есть два времени:

- `valid_from` / `valid_to` — предполагаемый или подтверждённый период действия у банка,
  полуоткрытый интервал `[from, to)`;
- `recorded_at`, `published_recorded_at`, `superseded_at` — когда система записала, опубликовала
  и заменила эту версию; `last_seen_at` фиксирует повторное обнаружение тех же правил.

В рамках одной программы запрос выбирает опубликованную ревизию, подходящую под `as_of`.
`known_at` дополнительно ограничивает выбор теми версиями, которые были опубликованы и ещё не
заменены на тот момент. Категория идентифицируется `program_id + source_key`, а не названием.
Включения, исключения конкретной категории, глобальные исключения и немаппируемые в MCC условия
хранятся раздельно. При будущем расчёте глобальный запрет должен иметь приоритет над включением
в категорию, а категорийный запрет — над её включением. Этот порядок реализован в проверке
кода покупки (`GET /api/mcc/{code}/bank-rules`); выбор лучшей карты пока не реализован.

## Что ещё не готово и что делаем дальше

1. **Надёжность исторических данных.** Запретить конфликтующие опубликованные интервалы и
   определить правило замещения версий с различными `valid_from`; сейчас публикация заменяет
   открытую версию лишь при одинаковом `valid_from`, а запрос при пересечении выбирает наиболее
   поздний подходящий старт. Добавить diff, проверку резкого исчезновения правил, отклонение
   черновика и обработку ошибок источника без риска опубликовать пустой набор.
2. **Полноценный редактор.** Сейчас интерфейс редактирует MCC, категории и общие поля, но не
   предоставляет отдельной формы для создания/изменения текстовых условий. Условия из базовой
   ревизии сохраняются при копировании. Нужны просмотр источника и diff перед публикацией.
3. **Источники данных.** Отдельно согласовать официальный справочник MCC и источники правил по
   каждому банку/программе. Добавить парсеры публичных страниц, PDF или доступных API, хранение
   первичного текста/файла, расписание проверки, версии парсеров, тестовые фикстуры и
   наблюдаемость. Только после этого подключать реальную работу кнопки автозагрузки. Не выводить
   «полный список» из неполного текста.
4. **Связь с текущим кешбэком (следующий продуктовый этап).** Сопоставить персональное
   `cashback_category` с банковской категорией/ревизией, сохранив исходное название и месячный
   выбор. Затем использовать правила для сравнения категорий и рекомендации карты для покупки
   по известному MCC; учитывать ограничения оплаты, дату и неопределённость.
5. **История операций (более поздний этап).** Подключить банк или платёжный источник,
   импортировать операции и фактически наблюдавшиеся MCC. Хранить соответствия продавца и MCC
   отдельно от официальных правил; при повторной покупке показывать прошлую операцию и
   обоснованную рекомендацию карты.
